# RewaPay x Cray: Interface Contract (v0.1)

Date: 10 November 2026

## 1. Purpose

This document defines what the Cray integration module exposes to RewaPay's wallet, and what it needs back from the wallet. It is a starting contract. Names and shapes are proposed. Changes are welcome, and you should propose them in your plan (`STATUS.md`, first entry) before building the wallet side.

The module is built as an in-process NestJS module. Operations are methods on a TypeScript service interface. Events are emitted through the module's event mechanism. No network service is involved.

## 2. Shared concepts

| Concept | Type | Rules |
|---|---|---|
| `customerId` | string | RewaPay's customer identifier. Opaque to the module. |
| `walletId` | string | RewaPay's wallet identifier. Opaque to the module. |
| `reference` | string, max 64 chars | Unique per money-moving operation. Generated by the caller. Used for idempotency and correlation. |
| `amount` | decimal string | NGN, two decimal places, for example `"100.00"`. Never a float. |
| `currency` | string | Always `"NGN"` in v0.1. |
| `status` | enum | `PENDING`, `PROCESSING`, `SUCCESSFUL`, `FAILED`. |
| timestamps | string | ISO 8601, UTC. |

## 3. Operations (called by the wallet)

Each operation returns a result or an error (section 6). Exact names are proposals.

**Virtual accounts**

- `createVirtualAccount({ customerId, fullName, email, bvn })` returns `{ accountNumber, accountName, bankName, status }`. The provider may first require an OTP. In that case, return `status: "OTP_REQUIRED"`.
- `submitVirtualAccountOtp({ customerId, otp })` returns `{ status }`.
- `getVirtualAccount({ customerId })` returns the account details, or `NOT_FOUND`.

**Funding**

- `createFundingSession({ customerId, walletId, amount, reference, method })` returns `{ sessionId, paymentUrl, expiresAt }`. `method` is `"card"` or `"bank_transfer"`. Card payments go through hosted checkout unless RewaPay approves otherwise.
- `getFundingStatus({ reference })` returns `{ status, amount, confirmedAt? }`.

**Banks and transfers**

- `listBanks()` returns `[{ code, name }]`.
- `validateBankAccount({ accountNumber, bankCode })` returns `{ accountName }`.
- `initiateTransfer({ walletId, amount, reference, destination: { accountNumber, bankCode, accountName } })` returns `{ transferId, status }`. The wallet debit is handled by the wallet. This operation sends the money.
- `getTransferStatus({ reference })` returns `{ status, amount, failureReason? }`.

**Refunds (scope to be confirmed)**

- `initiateRefund({ reference, amount })` returns `{ refundId, status }`.

**Operations (internal use)**

- `getPlatformBalance()` returns `{ currency, available }`.

## 4. Events (emitted by the module to the wallet)

Each event describes a fact that has been confirmed with the provider. Events are delivered at least once. The wallet must deduplicate on `eventId`.

| Event | Fields |
|---|---|
| `funding.confirmed` | `eventId`, `customerId`, `walletId`, `reference`, `amount`, `currency`, `confirmedAt` |
| `funding.failed` | `eventId`, `reference`, `reason`, `failedAt` |
| `transfer.completed` | `eventId`, `transferId`, `reference`, `amount`, `currency`, `completedAt` |
| `transfer.failed` | `eventId`, `transferId`, `reference`, `reason`, `failedAt` |
| `refund.completed` | `eventId`, `refundId`, `reference`, `amount`, `currency`, `completedAt` |

## 5. Rules for money movement

1. **Idempotency.** A repeated call with the same `reference` returns the original result. It must not repeat the money movement.
2. **Confirm before crediting.** A funding event is emitted only after the provider's status is confirmed. An incoming webhook alone is not enough. Verify the webhook signature, then query the provider for the authoritative status.
3. **Credit once.** The wallet credits a funding event at most once, keyed on `eventId` and `reference`.
4. **No silent failures.** Every failure returns a typed error or emits a failed event with a reason. Nothing is left in an unknown state without a way to query it.
5. **Reconciliation.** The module must be able to re-query any `PENDING` or `PROCESSING` item and reach a final status.

## 6. Errors

Every error has this shape:

```json
{ "code": "PROVIDER_UNAVAILABLE", "message": "human-readable text", "retryable": true, "providerCode": "optional" }
```

Suggested codes: `INVALID_INPUT`, `NOT_FOUND`, `DUPLICATE_REFERENCE`, `OTP_REQUIRED`, `OTP_INVALID`, `PROVIDER_REJECTED`, `PROVIDER_UNAVAILABLE`, `INSUFFICIENT_FUNDS`.

## 7. Sensitive data

- BVN, OTP, card data, and full bank details are passed through to the provider only.
- They are never stored in plain text, never written to logs, and never returned to the wallet.
- Card data is handled by hosted checkout by default. Any direct card handling needs RewaPay's written approval first.
- Logs record the operation, the `reference`, the status, and the provider's response with sensitive fields masked.

## 8. Open decisions for your plan

1. Confirm or change the operation and event names above.
2. How provider responses are stored for audit, and for how long.
3. The reconciliation schedule and how stuck items are surfaced.
4. The refund scope, including whether it is part of the first release.
5. Whether `amount` should be kept in NGN with two decimal places, or in minor units. Propose one and justify it.
